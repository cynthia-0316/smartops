Which engines need maintenance?

We scored 99 model configurations that predict Engine Condition (Normal vs Needs Maintenance) from six engine sensors. This page collects every finding, figure and result from the project so far.

Dataset: jskswamy/predictive-maintenance-data (Hugging Face)Team: Uzair, Rishabh, Cynthia, Xin, Noah
The short answer

Every good model lands at the same score, about 0.71 AUC

What we found

  • Best model: a GAM (a smooth curve per sensor, added up). It ties the best gradient-boosting models and is faster, easier to explain and well calibrated.
  • The limit is the data, not the algorithm. Boosting, neural nets, random forests, stacks and ensembles all stop at 0.703 to 0.705 cross-validated AUC and about 0.71 on the test set. Models that can learn sensor combinations do no better than ones that can't.
  • Engine RPM carries most of the signal. Low RPM goes with "Needs Maintenance". Fuel pressure, lub oil temperature and lub oil pressure add a little; the coolant sensors add almost nothing.
  • The business gain is modest. 63% of engines are labelled "Needs Maintenance", so random picking is already right 63% of the time. The model's top 10% is right about 91% of the time.
1 · The data

Six sensors, one label, no missing values

Each row is one reading from a diesel engine: RPM, three pressures and two temperatures, plus a label. The data is a public Hugging Face upload. It does not say how it was collected or how "Needs Maintenance" was decided.

Class balance

Most rows are labelled "Needs Maintenance". This is not a rare-failure problem: a model that flags every engine is already right 63% of the time.

How the data was split

All tuning and model choice used train + validation (16,604 rows) with cross-validation. The test set was held back for final checks only.

Spearman correlation between sensors. No pair goes beyond ±0.09, overall or within each class. Real engine sensors usually move together (RPM and pressures, for example), so this pattern suggests the data may be synthetic.

2 · How models were compared

One protocol for every model

All results come from the shared code in src/common.py, so every model saw the same data and the same folds.

Data

Train + validation

16,604 engines. The 2,931-engine test set stays locked.

Cross-validation

5 folds × 3 repeats

15 train/score rounds with seed 42. Scores are the mean and spread over the 15 folds.

Tuning

Nested CV

Settings are searched only inside each training fold, so the reported score is not inflated by the search.

Metric

ROC AUC first

How well the model ranks engines by risk. F1 is misleading here: flagging every engine gives F1 0.77.

Comparison

Paired tests

Models are compared fold by fold with a corrected resampled t-test.

4 · Why everything plateaus

The signal is weak and adds up sensor by sensor

Flexible models barely beat simple ones

Engine RPM alone reaches 0.67, and plain linear logistic regression is close behind the GAM. Letting the model bend its curves adds a little; nothing beyond that adds more.

Evidence

What this means. Gradient boosting is strong because it finds interactions between features. Here there are none to find, so a simple additive model does just as well. More tuning or bigger models will not move the score; better data would.

    When does the model save money?

    Costs are assumptions (the data has none): an unneeded inspection costs 1, a missed fault costs r. The model only clearly beats "inspect everything" when a miss costs about as much as an inspection.

    8 · Limits and next steps

    What to keep in mind

    Limitations

    • Unknown origin and label. The data's source and the meaning of "Needs Maintenance" are not documented. The near-zero correlations suggest synthetic data.
    • No engine ID or time. We cannot group readings by engine or follow trends, so scores may be optimistic if one engine appears in both train and test.
    • No cost data. The money analysis uses assumed costs.
    • One test set, several looks. Fine for reporting, but it should not be used again for choosing models.

    Next steps

    • Adopt the GAM (or the spline logistic regression) as the final model and update the report section from #18.
    • Finish #17 (other model families) and #6 (data exploration write-up); coordinate with the improvement experiments, which already cover several #17 models.
    • Ask whether better data exists: engine IDs and timestamps, a documented label, real inspection and failure costs.
    • Merge the improvement work (experiments/) through a reviewed pull request.
