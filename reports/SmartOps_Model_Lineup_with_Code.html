Every model we tried, and what each one taught us

We ran 99 model configurations from 9 families to predict whether an engine needs maintenance from six sensor readings. Each family below explains how the model works, the variations we tried, and the score each variation got. The short version: once a model can bend its curves, they all land in the same place, about 0.70 AUC.

Results come first. The complete Python code behind them is in the Code & Reproducibility Appendix at the bottom. The official course submission is the executed Colab export, SmartOps_Final_Colab_Analysis.html; this page is the presentation version.

Before the details

How to read the scores

ROC AUC

Pick one engine that needs maintenance and one that doesn't. AUC is the chance the model gives the first one the higher risk score. 0.50 is a coin flip and 1.00 is perfect. Our models sit around 0.70: they rank the right engine higher about 70% of the time.

Cross-validation

Every score comes from the 16,604 training and validation rows, split 5 ways and repeated 3 times (15 fits). Each fit is scored on rows it never saw, and the 15 scores are averaged. The 2,931-row test set was kept aside and used only for the final models.

Fair comparisons

When we tune settings and score on the same folds, the score is slightly flattering. Nested cross-validation tunes inside each training fold instead, so the score is fair. Hollow dots mark the flattering kind. The bias is about 0.001.

Is a difference real?

We compared models fold by fold with a corrected t-test. Almost every gap between the good models was too small to be more than chance.

What the variations told us

Lessons

  • Bending curves is what matters. Moving from straight-line logistic regression (0.688) to any model with curved effects (about 0.703) is the only big jump in the whole project.
  • Sensor interactions add nothing. Models that can combine sensors (boosting, forests, neural nets) tie models that can't (GAM, naive Bayes). Explicit interaction terms gained +0.0003 to +0.0008, and none was significant. The sensors are close to independent: no pair correlates above 0.09.
  • Tuning matters for boosting, not for additive models. XGBoost went from 0.662 to 0.702 with tuning. Spline and GAM settings move the score by only 0.002.
  • Simpler settings win. Every boosting library chose tiny trees, and deeper CatBoost trees did steadily worse. Engineered features and feature selection made things slightly worse.
  • Combining models doesn't help. They all learn the same additive pattern and make the same mistakes, so averaging gains at most +0.0005.
  • The limit looks like the data, not the algorithm. Nine very different families converge on 0.703 to 0.705, and models that can learn sensor combinations do no better than ones that can't. Bigger gains would most likely need new information: more sensors, readings over time, or cleaner labels.
  • Two deployable choices, no proven winner. The GAM with 20 splines has the best single-model CV score (0.7041, test 0.7095) and chooses its own smoothing. The dashboard deploys the spline logistic regression (CV 0.7032 at its fixed setting, 0.7026 nested; test 0.7099) because it is transparent and light enough to run inside a browser. The gap between them is not significant (CV +0.0009, p = 0.21; test difference −0.0004, 95% CI −0.002 to +0.001), so a slightly higher test AUC is not evidence that one is better.
Why it matters

What this means for SmartOps

SmartOps helps maintenance teams decide which engines to inspect first when inspection capacity is limited. These experiments answer which kind of model is worth deploying for that job.

  • Interpretability and simple deployment beat a fraction of a percent. Nine families land within about 0.002 AUC of each other, so the choice rests on other qualities. A spline logistic regression is a small set of knots and weights: a planner can inspect each sensor's curve, and the dashboard evaluates it in the browser with no server.
  • Scores support inspection prioritisation. They are not diagnoses. A high score means an engine resembles past engines labelled “needs maintenance”; it says nothing about which component is at fault.
  • Cost-saving scenarios are hypothetical. The data has no cost information. With cheap unneeded inspections the model can beat “inspect everything”; once a missed fault costs about three times an unneeded inspection, the cost-optimal rule flags almost every engine (see code appendix, Section K).
  • Human review is required. About a third of flagged engines are false alarms at any reasonable threshold, and AUC near 0.71 is a ranking aid, not a verdict.
  • Provenance is uncertain. We do not know where the data came from, whether it is real or synthetic, or exactly how “needs maintenance” was defined, and there is no time or engine identifier. Treat every number here as a property of this dataset.
Evidence and protocol

How to trust each number

Data separation

19,535 engines in total: 16,604 development rows (train + validation) for every model choice, and 2,931 held-out test rows opened once, after the choices were fixed. No threshold or setting was tuned on the test set.

Three kinds of CV score

Nested: tuning happened inside each training fold (fair). Fixed setting: no tuning on these folds (fair). Same-fold selection: settings were chosen on the same folds (hollow dots, slightly optimistic). Never compare them as if they were the same.
